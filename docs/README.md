# 1. 文档索引的用途

ZRAG 的设计文档并不是在项目完成后一次性补写的说明书，而是在开发过程中随设计决策逐步沉淀下来的工作记录。每一个模块的接口、每一处技术选型、每一次方案对比，都先以对话或设计稿的形式被记录下来，再被整理进架构文档与需求文档。因此，`docs/` 目录下的内容与代码是同步演进的：代码改到哪一层，相关文档通常也停留在对应的认知阶段，二者共同构成项目的完整知识资产。

本索引的作用，是为这些分散的文档提供一个固定的入口和一份可信的导航。它回答三个问题：有哪些文档、每份文档分别适合谁读、以及按什么顺序读最省时间。根目录 `README.md` 面向的是「第一次接触项目、想把它跑起来」的读者，本文件面向的是「已经跑起来、想理解它为什么这样设计」的读者。

需要提前说明一点：文档存在时效性差异。`design.md` 是对当前实现的权威描述，`PRD.md` 与 `PLAN.md` 记录的是需求与实现计划的演进过程，`QA/` 则是原始设计对话的历史存档。三者冲突时，一律以 `design.md` 的正文和当前代码为准，这一点在后文各文档简介与维护约定中会反复强调。

# 2. 文档地图

## 2.1 按读者角色划分

文档按读者角色分为三组。之所以按角色而不是按文档类型来组织，是因为同一份文档对不同读者的价值并不相同：例如 `design.md` 对使用者是「系统怎么运转」的说明，对贡献者则是「改动某个模块前必须对照的接口契约」。下表给出全局地图，随后三小节分别展开每组的阅读目的与推荐顺序。

| 角色 | 核心文档 | 辅助文档 | 阅读目标 |
|------|---------|---------|---------|
| 使用者 | [README](../README.md)、[design.md](design.md)、[diagrams/](diagrams/) | [PRD.md](PRD.md) | 理解系统能力、部署方式与整体架构 |
| 贡献者 | [design.md](design.md)、[PRD.md](PRD.md) | [PLAN.md](PLAN.md)、[QA/](QA/index.md) | 理解模块边界、实现约束与决策来由 |
| 维护者/研究者 | [PLAN.md](PLAN.md)、[QA/](QA/index.md) | [design.md](design.md)、[adr/](adr/README.md) | 追溯演进过程、切片依赖与备选方案 |

## 2.2 使用者

使用者关心的是「这套系统能做什么、怎么部署、请求进入后流经哪些组件」。根目录 `README.md` 已经覆盖了快速上手所需的环境变量、启动命令与 API 端点清单，因此本组文档的定位是补充「为什么这样设计」与「组件之间如何协作」。

推荐顺序是先读根目录 `README.md` 的架构图与配置说明，建立组件级的直觉；再读 `design.md` 的第 1 至 3 章，理解设计目标、核心概念与存储层；最后按需打开 `diagrams/` 中的架构图，对照 `design.md` 的正文确认各组件关系。`PRD.md` 在这一组中是选读项，适合想了解产品能力边界（哪些在多轮对话、查询改写、摘要压缩上做过增强）的用户。

| 文档 | 路径 | 适合谁读 | 阅读顺序 |
|------|------|---------|---------|
| 系统架构设计 | [design.md](design.md) | 希望理解系统全貌的使用者与开发者 | 第 1 至 3 章 |
| 架构图 | [diagrams/](diagrams/) | 偏好图形化理解组件的读者 | 配合 design.md 第 1、9 章 |
| 产品需求文档 | [PRD.md](PRD.md) | 想了解功能范围与用户价值的读者 | 选读，可与 design.md 对照 |

## 2.3 贡献者

贡献者面对的是「我要改的这个模块，它的上游和下游分别是什么、接口约定在哪里」。这一组文档的主线是：`PRD.md` 说明需求与实现决策，`design.md` 给出模块级的接口与流程，`QA/` 保留这些决策形成时的讨论与备选方案，`PLAN.md` 则标明了各模块的切片编号与依赖关系，便于判断改动会影响哪些下游切片。

推荐顺序是先通读 `PRD.md` 的「解决方案」与「实现决策」两节，确认改动是否符合产品定位；再在 `design.md` 的目录中找到对应模块章节精读；如果该模块在 `QA/` 中有专题记录，读一遍该专题可以避免重复踩坑；最后用 `PLAN.md` 的切片依赖表确认改动波及的范围。

| 文档 | 路径 | 适合谁读 | 阅读顺序 |
|------|------|---------|---------|
| 产品需求与实现决策 | [PRD.md](PRD.md) | 所有准备改代码的人 | 先读「解决方案」「实现决策」 |
| 系统架构设计 | [design.md](design.md) | 所有准备改代码的人 | 精读对应模块章节 |
| 设计对话记录 | [QA/](QA/index.md) | 想了解某决策来龙去脉的人 | 按专题查阅 |
| 实现计划与切片 | [PLAN.md](PLAN.md) | 需要判断改动影响面的人 | 查依赖表 |

## 2.4 维护者与研究者

维护者与研究者关注的不是「怎么用」，而是「为什么变成现在这样、当初还考虑过什么」。`PLAN.md` 保留了从项目骨架到多轮对话优化的切片序列与依赖关系，是理解实现顺序的第一手材料；`QA/` 按主题存档了设计对话，包含被否决的方案与折中取舍；`adr/` 则按编号记录了架构决策，其中 0001 号是一份尚未实施的 ChromaDB 迁移提案，适合作为「已知但未采纳的改进方向」来阅读。

推荐顺序是先看 `PLAN.md` 的「全部切片」与「开发进度」两节，建立时间线；再进入 `QA/index.md`，按分类找到感兴趣的专题；最后回到 `design.md` 确认该专题在当前实现中的最终形态。需要牢记：`QA/` 中的结论可能已被后续实现覆盖，它记录的是「当时的判断」，而不是「现在的契约」。

| 文档 | 路径 | 适合谁读 | 阅读顺序 |
|------|------|---------|---------|
| 实现计划 | [PLAN.md](PLAN.md) | 维护者、想复盘项目节奏的人 | 先读切片表与开发进度 |
| 设计对话记录 | [QA/index.md](QA/index.md) | 研究者、需要决策背景的人 | 先看分类索引再进专题 |
| ChromaDB HTTP 迁移提案（ADR 0001） | [adr/0001-chromadb-http-server.md](adr/0001-chromadb-http-server.md) | 关注后续演进方向的人 | 选读，注意其未实施状态 |
| 系统架构设计 | [design.md](design.md) | 需要最终结论的人 | 作为校验基准查阅 |

# 3. 各文档简介

## 3.1 design.md

[design.md](design.md) 是项目的系统架构设计文档，也是 `docs/` 目录中体量最大、权威性最高的一份（当前约 3250 行，共 13 章）。它以「本地优先、隐私保护」为设计前提，依次讲述了问题陈述与设计取舍、核心概念（摄入管道、混合检索、RAG 问答、会话管理）、存储层、Embedding 模型、文档摄入、检索层、LLM 集成、API 设计、前端设计、Trace ID 追踪、配置管理、日志体系与扩展点。每一章都在解释「为什么这样设计」，而不仅是罗列接口，因此它同时也是理解项目工程判断的主要来源。

在文档链路中，`design.md` 位于 `PRD.md` 的下游、`PLAN.md` 的上游：`PRD.md` 定义要做什么，`design.md` 定义如何实现以及为何这样实现，`PLAN.md` 再把这些实现拆成可独立验收的切片。`QA/` 中的专题讨论则是 `design.md` 的原始素材，二者的关系类似会议纪要与最终决议。当你在任何一份文档中看到相互矛盾的描述时，应以 `design.md` 的正文和当前代码为准，因为它随实现更新得最及时。

适合阅读它的时机包括：准备修改某个模块之前、需要向他人解释系统架构时、排查跨模块问题时，以及想确认某项能力是否已在设计中覆盖时。它的目录结构清晰，可以按章跳读，不必从头到尾线性阅读。需要提醒的是，文档中的代码片段用于说明设计意图，可能省略了错误处理与边界判断，实际行为仍以 `zrag/` 下的源码为准。

## 3.2 PRD.md

[PRD.md](PRD.md) 是产品需求文档，篇幅约 430 行，结构上分为问题陈述、解决方案、用户故事、实现决策、测试决策与「不在范围内」几部分。它回答的核心问题是：这个系统为谁解决什么问题，以及为了这些问题做了哪些明确的实现选择。用户故事以「作为某类用户，我希望……以便……」的形式列出了三十余条需求，覆盖摄入、检索、多轮对话、查询改写、摘要压缩、Web UI、部署与运维等场景，是判断某项功能是否属于产品范围时的第一依据。

在文档链路中，`PRD.md` 是 `design.md` 与 `PLAN.md` 的上游。它的「实现决策」一节已经给出总体架构与技术选型的结论（例如原生 Python、Django REST Framework、Vue 3、uWSGI、LiteLLM Gateway、Ollama 本地模型等），`design.md` 负责把这些结论展开成可实现的模块设计，`PLAN.md` 再按模块切成切片。「不在范围内」一节同样重要：它明确划定了当前阶段不处理多用户隔离、不引入消息队列做异步摄入、不部署分布式向量检索集群等边界，避免读者把后续演进方向误当作现有能力。

适合阅读它的时机包括：判断一个新需求是否值得做、需要向外部介绍产品能力边界、或在实现中遇到「这个功能到底该不该有」的争议时。需要注意，`PRD.md` 描述的是需求与决策的累积结果，部分早期条目在实现过程中被后续优化覆盖（例如检索权重、分块参数经过多轮调整），具体参数值应以 `design.md` 的对应章节和配置文件为准。

## 3.3 PLAN.md

[PLAN.md](PLAN.md) 是实现计划文档，核心内容是一张按依赖关系组织的切片表。每个切片都有编号、名称、类型（AFK 或 HITL）与依赖项，并遵循「上游切片未 merge，下游不启动」「抽象类先于实体类」等规则。文档头部记录的最后更新时间为 2026-06-19，正文除了最初的 45 个基础切片外，还陆续追加了 macOS Notes 异步文件桥接（#46-#61）、混合检索准确度优化（#62-#72）、RAG 回答质量优化（#101-#108）、多轮对话优化（#110-#117）、摘要压缩 prompt 大小动态限制（#120-#123）以及摘要内容格式调整（#124、#125）等增量切片。

在文档链路中，`PLAN.md` 承接 `PRD.md` 的需求与 `design.md` 的设计，把「要做的事」拆成可独立验收的工作单元，因此它是三者中最偏执行层的一份。它的价值不在于描述最终形态（那由 `design.md` 负责），而在于保留实现顺序与依赖约束：当你想知道某个模块为何先于另一个模块出现、某次重构影响了哪些切片、或某个功能是在哪个阶段引入的，切片表和开发进度是直接的证据。

适合阅读它的时机包括：准备按切片方式继续开发、需要评估一项改动的波及范围、或复盘项目节奏与决策顺序时。需要注意，切片表是计划而非现状，部分切片可能在实施中被合并、拆分或调整，实际完成情况应以代码与 `design.md` 为准；「开发进度」一节只反映记录当时的状态，不保证持续更新。

## 3.4 QA/ 设计对话记录

[QA/](QA/index.md) 目录是设计对话的原始存档，由早期的单一 `QA.md` 按主题拆分而来（`QA.md` 已移除），当前包含一个索引文件 [index.md](QA/index.md) 与八个专题文件。索引按「数据源与摄入」「存储与 Embedding」「检索与 LLM」「混合检索准确度优化」「RAG 回答质量优化」「API 与会话管理」「日志 JSON 格式改造」「前端与部署运维」八类组织，每个专题文件内以 Q 编号标记一次独立的问答。它是理解「某个决策当初为什么这样定、还考虑过哪些被否决的方案」的最佳入口。

在文档链路中，`QA/` 位于 `design.md` 的上游，是设计成文的原材料。`design.md` 中的许多取舍——例如为何选择本地 Embedding、为何用 RRF 融合双路检索、为何引入本地小模型做查询改写、为何把日志改成全量 JSON——在 `QA/` 的对应专题中都能找到更完整的讨论过程和备选方案对比。反过来说，`QA/` 的结论并不保证与当前实现一致：专题记录的是对话发生时的判断，后续实现可能已经修正或推翻了其中部分内容。

适合阅读它的时机包括：想深入理解某个设计决策的来龙去脉、需要评估是否重新采纳某个曾被否决的方案、或在 `design.md` 中读到一个不直观的选择而想确认其理由时。使用时有两点需要特别注意：其一，`QA/` 是历史记录，与 `design.md` 冲突时以后者为准；其二，索引中「按 Q 编号查找」的方式目前存在编号冲突（详见第 5 节），定位时应结合文件名与编号，而不是只凭编号全文搜索。

## 3.5 diagrams/ 架构图

[diagrams/](diagrams/) 目录存放系统的架构图源文件，当前共有三份 `.drawio` 文件，分别覆盖系统架构、模块流转与部署架构三个视角。它们由 draw.io 生成，属于可编辑的源文件而非导出的图片；仓库中没有提交对应的 PNG 或 SVG 渲染产物，因此 GitHub 的 Markdown 预览无法直接显示图形，需要用 draw.io 或支持 `.drawio` 的编辑器打开。图形直观、便于沟通，但精确的接口、字段与流程细节仍以 `design.md` 的正文为准。

在文档链路中，`diagrams/` 是 `design.md` 的图形化补充，而不是独立的权威来源。三份文件与 `design.md` 的章节大致对应：`01-system-architecture` 对应第 1 章的系统架构全景，`02-module-flow` 对应核心概念与检索、摄入流程，`03-deployment-architecture` 对应部署与容器拓扑。由于图文件的修改成本高于正文，它们通常滞后于实现，阅读时应把图当作「帮助建立整体印象的辅助材料」，把 `design.md` 当作「回答问题时的依据」。

适合阅读它的时机包括：初次接触项目、需要向他人快速讲解架构、或在评审中讨论组件边界时。使用时需要注意，这些图生成于 2026-05-31，早于后续的摄入任务、查询改写、摘要压缩等模块（具体影响见第 6 节）。如果发现图中缺少某个当前已存在的组件，并不代表该组件不存在，而只说明这张图尚未随之更新。

## 3.6 adr/ 架构决策记录

[adr/](adr/README.md) 目录存放架构决策记录（Architecture Decision Record），当前包含一份索引 [adr/README.md](adr/README.md) 与一篇决策记录 [adr/0001-chromadb-http-server.md](adr/0001-chromadb-http-server.md)。索引说明了 ADR 的用途、四位递增的编号规则、四种状态取值（Proposed / Accepted / Deprecated / Superseded）、决策索引表以及新增 ADR 的流程；每篇记录则按「状态、日期、决策者、背景、决策、备选方案、后果、当前状态」的结构保存一项架构决策的完整上下文。

ADR 与 `design.md`、`QA/` 的分工值得说明：`design.md` 描述系统当前如何实现，随代码同步更新；`QA/` 是讨论过程的原始存档，原则上不回改；`adr/` 则固定记录「为什么做出某个架构选择」，并以状态字段标明该选择处于提案、生效还是被取代。三者中若出现冲突，现行实现仍以 `design.md` 与代码为准，ADR 的「当前状态」一节会明确指出其与代码的关系。

当前唯一的记录是 0001 号《ChromaDB 迁移为独立 HTTP 服务》，它由原 `docs/chromadb-http-server.md` 方案文档整理而来，状态为 `Proposed`，意味着**方案尚未实施**：`docker-compose.yml` 仍只有 frontend 与 backend 两个服务，`zrag/store/vector_store.py` 仍使用 `chromadb.PersistentClient` 嵌入式运行。记录中完整保留了原方案的端口、镜像版本、环境变量、容器配置、验证方法与回滚步骤，适合在计划对向量存储做独立运维改造或评估引入独立 Chroma 服务时阅读；任何与当前代码不一致之处，均以 `docker-compose.yml` 与 `zrag/` 源码为准。

# 4. 阅读路径建议

面对一个包含架构文档、需求文档、计划文档与对话存档的目录，最容易犯的错误是从头线性通读，结果在细节中迷失。下面给出三条典型路径，分别对应「想快速理解系统如何工作」「想参与开发」「想追溯某个决策的来龙去脉」三类目标。这三条路径并不互斥，可以按需组合。

**路径一：想快速理解系统如何工作。** 先读根目录 [README](../README.md) 的架构图与「技术栈」一节，建立「Nginx → 前端 → 后端 → SQLite/ChromaDB/LLM Gateway」的组件直觉；再读 [design.md](design.md) 的第 1 至 3 章，理解设计目标、核心概念与存储层；如果需要图形辅助，打开 [diagrams/01-system-architecture.drawio](diagrams/01-system-architecture.drawio)。这条路径大约需要半小时到一小时，足以支撑日常使用与向他人介绍。

**路径二：想参与开发。** 先读 [PRD.md](PRD.md) 的「解决方案」「实现决策」与「不在范围内」三节，确认你要做的改动是否在产品范围内；再在 [design.md](design.md) 的目录中定位对应模块章节精读，重点关注接口定义、数据流与异常处理；然后查 [PLAN.md](PLAN.md) 的切片依赖表，确认改动波及的上游与下游；最后到 [QA/index.md](QA/index.md) 找到该模块的专题文件，读一遍历史讨论以避免重复已被否决的方案。这条路径建议配合源码阅读，遇到文档与代码不一致时以代码为准。

**路径三：想了解某个决策的来龙去脉。** 先查 [QA/index.md](QA/index.md) 的分类索引，按主题定位到具体专题文件；在专题文件中按 Q 编号找到对应问答，注意结合文件名定位而非只凭编号搜索（原因见第 5 节）；读完历史讨论后，回到 [design.md](design.md) 的对应章节确认该决策在当前实现中的最终形态。如果两份文档结论不同，说明决策在讨论之后发生了演进，应以 `design.md` 与代码为准，并可在 `QA/` 中寻找是否存在更晚的修正记录。

# 5. 文档维护约定

文档的价值取决于它是否可信、是否可导航。为了让 `docs/` 在长期演进中保持可用，约定以下几条维护规则。这些规则既约束未来的文档新增，也为当前状态提供一份诚实的说明——其中部分规则尚未在所有文档上落实，下文会如实指出。

**新增文档必须在本索引登记。** 任何在 `docs/` 下新增的 Markdown 文件或图源目录，都应在第 2 节的文档地图与第 3 节的简介中增加对应条目，说明其用途、读者与上游下游关系。未登记的文档会成为「孤立文档」，只能靠全文搜索发现，违背了本索引作为唯一入口的初衷。同样，删除或重命名文档时，必须同步清理本索引与其它文档中的引用。

**文档内的相对链接必须指向真实存在的文件。** 由于 `docs/` 中的文档会互相引用（例如本文件引用各专题、`design.md` 引用配置片段、`QA/index.md` 引用各专题），任何相对路径都应在提交前用 `ls` 或 `test -f` 验证。GitHub 对失效链接不会报错，只会静默地跳转到 404，因此这类问题往往要到读者点击时才被发现。本索引中的所有链接已在创建时逐一核对，指向的目标均真实存在。

**公开文档建议在顶部标注最后更新时间与适用状态。** 目前 `PLAN.md` 已在顶部标注「最后更新」，`adr/` 中的 ADR 统一设有状态与日期字段，`QA/index.md` 设有「最近更新」小节，但 `design.md` 与 `PRD.md` 尚未标注统一的更新时间。建议后续逐步补齐，并在需要时增加「适用状态」字段（例如「现行」「提案，未实施」「历史存档」），使读者在打开文档的第一屏就能判断其可信度。`adr/0001-chromadb-http-server.md` 的 `Proposed` 状态就是「提案，未实施」的一个示例。

**「按 Q 编号查找」存在编号冲突，需结合文件名定位。** `QA/index.md` 的查找方法建议「在对应文件中搜索 `Q{编号}`」，但当前多个文件独立编号，导致同一编号在不同文件中指向不同问答。经核对，冲突确实存在且不止一处：例如 `Q24` 同时出现在 `data-ingestion.md`、`rag-quality-optimization.md` 与 `index.md` 的更新记录中；`Q27`、`Q28` 同时出现在 `retrieval-llm.md` 与 `rag-quality-optimization.md`；`Q1`、`Q2`、`Q3` 等低编号也在 `data-ingestion.md` 与 `rag-quality-optimization.md` 中重复使用。因此，按编号搜索必须限定在正确的专题文件内，或直接使用「文件名 + 编号」的组合来定位；在冲突修复之前，不要假设某个编号在全局唯一。

**文档与代码冲突时以代码为准，并回头修正文档。** 文档是对实现的描述，不是实现本身。发现文档滞后时，应在同一次改动中更新文档，而不是留下已知的不一致。尤其是 `design.md`，它被本索引声明为权威来源，因此更需要在模块级改动后同步维护；`QA/` 则不同，作为历史存档，它的内容原则上不回改，只在实际结论被推翻时由 `design.md` 覆盖。

# 6. 图表说明

`docs/diagrams/` 下的三份 `.drawio` 文件是 draw.io 的可编辑源文件，而 GitHub 的 Markdown 渲染器不支持解析这种格式。这意味着在 GitHub 网页上直接点击这些文件，通常只能看到 XML 源码或下载提示，无法看到图形。要查看或编辑它们，需要下载后用 [draw.io](https://www.drawio.com/)（桌面版或网页版）打开；在本地开发环境中，也可以使用支持 draw.io 的编辑器插件打开。仓库当前没有提交 PNG、SVG 等渲染产物，因此没有「直接可预览」的版本。

这些图生成于 2026-05-31，早于项目后续的多个重要模块。具体来说，异步摄入任务与文件桥接、查询改写（含本地小模型）、上下文感知检索、对话摘要压缩、日志全量 JSON 化等能力，都是在这些图生成之后才引入或定型的。因此图中很可能缺少对应的组件、数据流或容器，或者保留了已被调整的旧结构。这不是图的错误，而是图未随正文同步更新的结果——图形文件的维护成本高于文字，项目选择了优先保证 `design.md` 的准确性。

因此，使用图表的正确方式是：把它当作建立整体印象和沟通讨论的辅助材料，而不是接口与流程的权威依据。当图中内容与 [design.md](design.md) 正文不一致时，一律以正文和当前代码为准；当需要在文档或评审中引用架构时，应同时注明图的生成时间与可能滞后的模块范围。如果未来重新生成这些图，建议在文件名或文档头部标注对应的代码版本或日期，使它和正文的时效性可以对照，而不是再次陷入「图新还是文字新」的不确定性。
