# 架构决策记录（ADR）

本目录存放 ZRAG 项目的架构决策记录（Architecture Decision Record，ADR）。一份 ADR 只记录一个经过论证的架构决策：它当时面临什么问题、最终选择了什么方案、放弃了哪些备选方案、以及这个选择带来了哪些后果。与 `docs/design.md` 描述「系统现在是什么样」不同，ADR 描述的是「系统为什么变成这样，以及哪些变化尚在提案阶段」。

---

## 1. 什么是 ADR

ADR 是一种轻量的决策文档格式，最初由 Michael Nygard 提出。它的核心价值在于把决策的**上下文**与**结论**一起保存下来：代码能说明系统做了什么，但无法说明当初为什么排除了其他做法、接受了哪些代价。当后来者质疑某个设计、或想重新采纳一个曾被否决的方案时，ADR 是比代码注释和聊天记录更可靠的依据。

一份 ADR 通常包含：状态、日期、决策者、背景、决策、备选方案、后果。本目录的 ADR 统一采用这一结构，并在需要时附加实施验证、回滚方案与当前状态等章节。

需要区分三类文档的职责：

| 文档 | 回答的问题 | 时效性 |
|------|-----------|--------|
| `design.md` | 系统当前如何设计与实现 | 随代码同步更新，是现行权威描述 |
| `QA/` | 某次设计讨论中各方怎么说 | 历史存档，原则上不回改 |
| `adr/` | 某个架构决策为何做出、状态如何 | 决策一旦记录即保持稳定，状态字段随实施推进更新 |

---

## 2. 编号规则

- 文件名格式为 `NNNN-<kebab-case-title>.md`，例如 `0001-chromadb-http-server.md`。
- `NNNN` 为四位十进制序号，从 `0001` 开始**单调递增**，永不复用，即使某份 ADR 被废弃或取代也不回收其编号。
- 标题部分使用英文小写与连字符，保持与文件名规范一致；ADR 正文中的一级标题使用「ADR NNNN: 中文标题」的形式。
- 编号在创建时分配，按决策的提出顺序而非实施顺序排列。

---

## 3. 状态取值

每份 ADR 头部必须标注状态，取值限定为以下四种：

| 状态 | 含义 |
|------|------|
| `Proposed` | 提案。方案已完成论证，但尚未实施；正文描述的是目标状态，不代表现有代码。 |
| `Accepted` | 已采纳。方案已实施或已正式生效，正文与当前实现一致（若有偏离，应在「实施记录」中说明）。 |
| `Deprecated` | 已弃用。方案曾经生效，但当前已不再推荐使用，且没有明确的替代决策。 |
| `Superseded` | 已被取代。存在一份更新的 ADR 取代本决策，头部应注明取代它的 ADR 编号。 |

状态变更时应同时更新本索引中的状态列。`Accepted` 转 `Superseded` 时，不要删除旧 ADR，保留其正文以维持决策链完整。

## 5. 新增 ADR 的流程

1. **确认是否确需 ADR**。只有影响系统结构、部署拓扑、外部依赖或跨模块契约的决策才值得记录；局部实现细节、参数调整应写入 `design.md` 或对应模块的注释。
2. **认领编号**。查看本索引末尾的最大编号，取下一个四位序号；即使前一编号尚未实施也不得跳号或复用。
3. **按模板撰写**。至少包含状态、日期、决策者、相关文档、背景、决策、备选方案、后果、当前状态九个部分。所有技术细节应来自实际代码、配置或已存档的讨论，不得凭空补充。
4. **在索引中登记**。向第 4 节表格追加一行，状态与正文头部保持一致。
5. **更新相关文档**。在 `docs/README.md` 的文档地图与简介中登记新 ADR；若 ADR 取代了某份旧文档，应同步清理旧路径的引用，避免悬空链接。
6. **状态随实施推进**。方案落地后将状态改为 `Accepted` 并补充实施日期与提交记录；若实施中偏离原方案，追加「实施记录」小节，而不是改写原始决策正文。
