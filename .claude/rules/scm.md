# 项目版本管理指南
该文档中描述了针对一个项目的版本管理以及SCM的使用规范.

## 版本号设计 — 混合方案

在实际项目中，请根据当前项目的场景与特点来合理的采用以下三层版本号体系，以实现兼顾对外沟通的直观性和内部技术管理的精确性。

### 1. CalVer方案

面向用户、客户、市场发布的版本号，使用日历化版本格式。

- **格式**: `YYYY.MM(.MICRO)`
- **示例**: `ZRAG 2025.06`、`ZRAG 2025.06.1`
- **说明**: 一眼可知发布时间和产品生命周期。MICRO 位在同一个自然月有多次对外发布时递增。

### 2. SemVer方案

面向开发团队、API 兼容性管理的技术版本号，使用语义化版本格式。

- **格式**: `MAJOR.MINOR.PATCH`
- **示例**: `2.3.1`
- **规则**:
  - **MAJOR**: 不向下兼容的 API 变更时递增
  - **MINOR**: 向下兼容的功能新增时递增
  - **PATCH**: 向下兼容的 Bug 修复时递增
- **前置标签（Pre-release）**: 可在 PATCH 后追加 `-alpha.N`、`-beta.N`、`-rc.N` 等标签，如 `2.4.0-rc.2`。
- **0.x 阶段规则（ZeroVer）**: 当 MAJOR 为 0 时，MINOR 可以承载不兼容变更，PATCH 仍为 Bug 修复。即 `0.MINOR.PATCH` 中，MINOR 递增不承诺兼容性。

### 3. 内部构建

由 CI/CD 系统自动生成的构建标识，用于追溯每次构建的来源。

- **格式**: `<SemVer>+<meta>`
- **示例**: `2.3.1+git.a1b2c3d`、`2.3.1+build.20250605.3`
- **meta 可选值**:
  - `git.<short-sha>` — Git commit 短哈希
  - `build.<YYYYMMDD>.<seq>` — 构建日期加当日序号

### 方案选择思路
- 对外营销版本：使用 CalVer（如 ZRAG 2025.06）
- 内部技术版本：使用 SemVer（如 2.3.1）
- 构建版本号：CI 系统自动生成递增序号或 Git commit SHA（如 2.3.1+git.a1b2c3d）

### 映射关系

- 一个对外营销版本可能包含多个内部技术版本的迭代。
- 每次对外发布时，将当前技术版本与营销版本在 Release Notes 中关联记录。
- 建议在项目文档或 `CHANGELOG.md` 中维护一份映射表，例如:

| 营销版本 | 技术版本 |
|----------|----------|
| ZRAG 2025.06 | 2.3.1 |
| ZRAG 2025.06.1 | 2.3.2 |
| ZRAG 2025.07 | 2.4.0 |
